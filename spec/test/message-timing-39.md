# #39 時刻欠損とモデル読み込みの調査

## 原因と修正

通常チャットでは渡されたqueuedAtは保存される。一方、スキル経路には時刻記録がなかった。通常チャット・固定/手順スキル・不明スキルに対する記録と、保留後の最初の送信/受信時刻維持を合成テストで確認した。
画面の新規送信はミリ秒とUTCを持つISO時刻へ変更し、DBには既存形式と同じローカルnaive時刻で保存する。
時刻を送らない旧画面/APIクライアントには根拠がないため送信時刻を作らない。過去の27件のqueued_at欠損がどのクライアントに由来したかは共通識別情報がなく断定できない。

## モデル読み込みの調査

既存ログの51要求のうち、読み込み1秒以上は5要求。前の完了から次の要求開始までの推定間隔が60秒未満の34要求では読み込み1秒以上は0。間隔300秒超の4要求では2要求が該当した。秒単位の完了時刻とelapsed_msから集計したため、間隔は概算でありログ外のモデル利用も追跡できない。
初回・長い間隔の要求と連続要求を区別して比較し、会話との相関やモデルが解放された直接の原因は断定しない。
個人情報を含まない短い入力で2回の連続要求も測定した。要求経過1141ms/109ms、モデル読み込み19ms/21ms、モデル総時間1123ms/92ms。モデルの強制解放や長時間の常時保持はせず、現行の保持設定を維持した。
読み込みが時間を占める場合、常時保持・保持時間延長・予熱はメモリ占有や電力と交換になる。現状では連続要求の読み込みは短いため、全要求で予熱を追加せず、必要な場合に利用者が保持設定を調整できる既存管理画面を使う。

## エラーと反映確認

サーバーエラーは別Issue #40で返答送信中の通信切断と分類され、PR #42で安全な再送とINFO扱いを実装・マージ済み。
#35は実際のWindowsでチャット表示中の非表示、最小化で表示、復帰で非表示を確認し、設定のハッシュも不変だった。

合成DB・偽Google・偽モデルを使う時刻記録テスト4件と、画面のISO時刻・キュー保持のJavaScriptテストが成功。全オフライン43 passed / 0 failed / 13 skipped、モデル込み56 passed / 0 failed / 0 skipped。
稼働用の会話やGoogleタスクに検証用データを追加しない。新しい画面での記録には再読み込みが必要。
