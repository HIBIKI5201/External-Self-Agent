# Issue #36 ログ診断の検証（2026-10-08）

## 対象と実装判断

`esagent/diagnose.py` はアプリの `db` / `server` を読み込まない独立CLIとした。
SQLiteを `mode=ro` / `query_only` と単一読取トランザクションで開き、会話本文をSELECTしない。
時間記録は #23 の `queued_at` / `received_at` / `started_at` / `finished_at` を使う。
DB・モデル・サーバーは別々の期間軸で集計し、共通IDのない相関は不明と表示する。
モデルログの記録停止設定は触らず、欠損時も停止理由は推測しない。

ファイル欠損・旧スキーマ・不正行は解析範囲と除外件数で表す。出力フィールドを限定し、自由文を転記しない。
既存ファイルの上書きと入力フォルダへの出力も拒否する。

## 合成データによる検証

`tests/test_diagnose.py` の6テストは実ログを使わない。架空の秘密文字列を本文・要求・応答・エラー・設定などに埋め、テキストとJSONの両方への混入を検査した。

- 完了件数、待ち時間の3区間、中央値/p95/最大、要求失敗件数、モデル/種別内訳。
- モデル `.1` とサーバー `.2` の読取、壊れたJSON行・不正な日時・不正な型・NaN・巨大整数。
- 期間の開始を含み終了を含まないこと、UTCとオフセット付き日時の一致、上位件数0。
- 入力ファイルなしでもDBや設定を作成しないこと、旧列の不足、破損DB、逆転した時刻。
- 明示的な新規保存、既存ファイル/入力フォルダへの保存拒否、引数検証。
- 読取前後で合成入力ファイルのハッシュが一致すること。
- 書込接続が生きているWALモードでも最新のコミットを読めることと、DB/WALのハッシュが変わらないこと。SQLiteの共有メモリによるロック管理はハッシュ比較の対象外。

## 限界

画面の送信時刻がない旧データは `created_at` を代用した総時間だけ測れる。完了時刻がない行は完了判定できない。
サーバーの受信までの時間に通信も含まれ、モデルの要求時間から特定の会話の原因は断定できない。
稼働中の各ファイルを読む時点は一致しない。既に削除されたローテーションは復元しない。
新規CLIだけの追加なので常駐アプリの置換・再起動は不要で、PR作成時点では未マージ。
