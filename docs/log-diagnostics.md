# ローカルログ診断（#36）

返事の遅さやエラーの傾向を、一度の実行で確認するための読み取り専用コマンド。
Python 3.12 の標準ライブラリだけで動く。サーバーの起動・再起動や Google/Ollama への接続は不要。

リポジトリのフォルダで実行する。

```powershell
python esagent/diagnose.py
python esagent/diagnose.py --since 2026-10-01T00:00:00+09:00 --until 2026-10-02T00:00:00+09:00 --top 5
python esagent/diagnose.py --json
python esagent/diagnose.py --json --output diagnostics.json
```

開発用 worktree から稼働用のデータを読みたいときは、入力先を明示する。

```powershell
python esagent/diagnose.py --data-dir C:\ESAgent\data --top 5
```

- `--data-dir`: デフォルトは、このコマンドを置いたリポジトリの `data/`。作業中のフォルダには依存しない。
- `--since` / `--until`: ISO 日時。開始を含み、終了を含まない。省略するとその側の制限なし。タイムゾーン省略時は、このPCのローカル時刻として扱う。オフセット付き日時も同じ時点に換算する。
- `--top`: 総時間を測れる完了メッセージの上位件数（既定10、0〜1000）。0なら内訳を省略する。
- `--json`: テキスト要約の代わりに JSON を標準出力へ出す。時間の単位はすべてミリ秒。
- `--output`: 指定時だけファイル保存。既存ファイルは上書きしない。入力データのフォルダ内への保存も拒否する。

## 指標と限界

| 項目 | 集計の意味 / 判断できる範囲 |
|---|---|
| 完了件数 | `role=user` かつ有効な `finished_at` を持つ行。期間は送信時刻で選ぶ。完了が期間外でも送信が期間内なら含む |
| 送信→完了 | `queued_at` → `finished_at`。送信記録がない旧データでは `created_at` を代用し、その出所を示す。代用した値から画面での待ち時間は測れない |
| 画面での待ち時間 | `queued_at` → `received_at`。画面の送信順番待ち・通信時間を含む。通信と画面待ちを分離した原因判定はできない |
| 処理待ち | `received_at` → `started_at`。前の処理・モデル準備待ちなどを含む。`wait_reason=model` は記録された準備待ち、`status` は待ち時間質問。その他は `unknown` |
| 返答作成 | `started_at` → `finished_at`。判断・操作なども含む全処理時間。モデル生成だけの時間とは一致しない |
| モデル要求 | 要求完了時刻 `at` で期間を選ぶ。`error` が空でない要求を失敗として数える。モデル名・要求種別（text/json/tools）ごとの内訳を表示 |
| `elapsed_ms` | クライアントが測った要求の経過時間 |
| `load_ms` / `total_ms` | Ollama が報告したモデル読込 / 総処理時間。失敗時などは記録仕様上0になる場合があるため、0だけで「読込なし」とは断定できない |
| サーバー警告・エラー | ログのヘッダー時刻で期間を選ぶ。WARNING、ERROR（CRITICALも含む）の件数と時刻。本文・トレースバックは出さない |

中央値・p95・最大値には有効な非負の測定値だけを使う。p95はソート後の `(n-1)×0.95` の位置を線形補間する。測定値がない場合、テキストは「測定なし」、JSONの統計値は `null`。欠けた時刻・逆転した時刻から時間を推測しない。不正な送信記録がある場合は `created_at` で期間を選べるが、その総時間は測定対象から除く。

旧DBで完了時刻の列がない場合、完了の有無は判断できない。未完了・完了記録なしの件数と不足列を示す。スキル等で時間記録が残らない行も同様に扱う。完了件数と総時間の測定件数は一致しない場合がある。画面とサーバーの時計がずれている場合も、記録を補正しない。

会話DBとモデルログには共通IDがないため、両者の件数は独立した集計。近い時刻に遅いモデル要求があっても、特定のメッセージの遅延原因とは断定しない。相関は常に `unknown` とする。

## 分析範囲と安全性

`esagent.db` はSQLiteの `mode=ro` と読取専用トランザクションで開く。アプリのDB初期化・マイグレーション・設定読込関数は使わない。DB・ログ・設定を変更せず、外部への送信も行わない。

モデルログは `llm-requests.jsonl` と `.1`、サーバーログは `esagent.log` と存在する数字のローテーション分を読む。各ファイルの状態、読んだ件数、期間内の件数、期間外の件数、不正で飛ばした件数を出す。サーバーログのヘッダー以外の行は `continuation_lines` として別に数える。削除済みのローテーションや実行中に追記された記録をすべて含む保証はない。各入力は別々に読むため、ファイル間の同時点スナップショットではない。

ファイル欠損・読取不能・旧スキーマ・壊れたJSON行は報告し、読める入力の集計を続ける。`llm_log:false` を変更したりログ記録を有効にしたりはしない。残っているログは過去の記録として解析する。モデルログがない場合は利用不可と示すが、設定停止・未記録・保持期間外を区別する証拠はない。

出力項目を限定し、会話本文、モデルへの入力・応答、エラー本文、OAuth情報、設定の値、入力ファイルの絶対パスは出さない。内訳に必要なモデル識別名だけは表示する（パス・URL・自由文は `unknown` に置換）。要求種別と待ち理由も既知の値だけを表示する。
診断結果には時刻とローカルDBのIDが残るため、GitHubへの自動添付は行わない。
