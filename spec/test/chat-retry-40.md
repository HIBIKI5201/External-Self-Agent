# Issue #40: 返答中の通信切断と再送

## 変更と確認範囲

要求IDを画面の送信待ちと一緒に保持し、処理開始の予約と処理結果をSQLiteへ保存する。同じ要求の再送は結果を再利用し、同時再送は最初の処理の完了を待つ。本文が違うIDの再利用は拒否する。処理途中で停止し結果が不明な予約は再実行しない。

送信時のConnectionErrorはINFOに分類し、同じ接続へ500を送らない。返答の途中切断は画面で通信失敗として再送する。処理本体の500も保存し、途中まで行った操作を自動で繰り返さない。待ち時間質問など異なる要求は再送待機用のロックに遮られない。

- `python -m compileall -q esagent tests`、JSONの検査、`git diff --check`: 合格。
- Pythonの再現テスト: 返答writeの接続中断後の再送でメッセージ・タスクは1件だけ、200→切断後に500は送らない。モジュール状態を再作成してもDBから結果を復元。同時再送、別要求、結果不明の中断、ID不正・本文不一致、保留・400・500結果の再利用も確認。

テストは隔離DBとGoogle API遮断を用いた。実Googleアカウントへの変更、本番DBへの書き込み、常駐アプリの再起動は行っていない。再現例は合成データのみ。

## 残る制約

旧画面やIDなしクライアントは互換対応のみで、再送重複防止には新しい画面の再読み込みが必要。localStorageが使えない場合、再読み込み後のキュー復元は保証できない。処理と結果保存の間のサーバー停止は原子的に復旧できず、利用者による履歴・タスクの確認を要する。予約・結果はローカルDBに保持し、自動削除しない（過去要求の再実行を防ぐため）。返事待ちの結果を再利用した場合、最新の返事は通常の履歴更新で表示する。

#39 の送信時刻欠損やモデル再読み込みの原因調査は別件として残る。今回の実ログから重複操作が起きたとは断定しない。
